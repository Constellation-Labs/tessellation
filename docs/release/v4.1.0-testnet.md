## Why This Release Exists

v4.0.0 shipped a forward-looking rebuild of how global state is committed (the Merkle Patricia Trie),
sized for a network whose state and feature set are growing. It validated cleanly on Testnet and
IntegrationNet, which are small, lightly-loaded environments. Under MainNet-scale load it behaved
differently: the network ran normally for several hours, then entered a degradation spiral it did not
recover from. Nodes became resource-constrained, fell behind, and could not catch back up, and
repeated coordinated cold restarts did not restabilize the cluster. Out of an abundance of caution,
MainNet was reverted to v3.5.12 (see [`v3.5.12-rollback-mainnet.md`](v3.5.12-rollback-mainnet.md)).

The failure was not traced to a single defect. What became clear is that **resource degradation
outpaced a consensus liveness model that was not built to absorb it.** The v4.0.0 engine relied on a
simplified stall detector: adequate for a small, fast, lightly-loaded network, but not designed for
widespread, sustained node degradation or for the larger state footprint the MPT is built to support.
Once enough nodes were behind, that model could not distinguish a slow node from a departed one, could
not return lagging nodes to the network frontier, and the cluster could not reconverge.

v4.1.0 addresses this in two parts, in the order the work was undertaken:

1. **Chain recovery.** A reliable path for a lagging node to recover to the network's current frontier.
   Necessary, but on its own not sufficient to hold the network stable under load.
2. **A rebuilt consensus liveness model.** A proper leader-based partially synchronous BFT engine, with
   quorum and timeout certificates and pacemaker-driven view synchronization, designed for a larger
   validator set and a growing state footprint rather than only today's network.

## What's New

### Rebuilt Global Consensus Engine (partially synchronous BFT)

The Global L0 consensus engine is now a **leader-based, partially synchronous BFT** protocol. At a high
level:

- **A single leader proposes each round**, the committee votes, and a quorum of signatures finalizes.
  This replaces the v4.0.0 model where facilitator selection and stall handling were driven by local
  heuristics that could diverge between honest nodes under normal timing skew.
- **A pacemaker advances the view when a round stalls.** If a leader is slow or absent, the round does
  not wedge: a quorum-certified view change (via a timeout certificate) rotates leadership
  deterministically and the round proceeds. Liveness no longer depends on every node making the same
  local judgement at the same instant.
- **Committee changes are consensus-agreed, not local.** Peers are added or removed from the active
  signing set only through quorum-certified evidence carried on the signed chain, applied at round
  boundaries. This is the single most important correctness change: the failure class behind most
  observed forks was honest nodes computing different committees or leaders from local state.
- **Committee structure.** The active set is partitioned into a bounded, quorum-bearing core and a
  wider signing tier that also earns rewards, with the remaining peers observing and validating. This
  keeps the expensive coordination step small while keeping participation and rewards broad.

The result is a liveness model that degrades gracefully: slow or absent nodes are routed around rather
than allowed to wedge the network, and a node that has fallen behind has a defined path back in.

> The threat model is explicit and unchanged from Constellation's operating assumptions: a **trusted,
> permissioned validator set subject to crash, GC, network, and partition faults**, not an actively
> adversarial one. The design optimizes for real operational degradation, which is what MainNet
> exhibited.

### Chain Recovery

Lagging nodes recover to the network frontier using validated chain information rather than local
guesswork, and recovery source-selection avoids the deadlock where recovering nodes ask other
recovering nodes for state that none of them yet holds. Rollbacks are directional and require
corroboration before a node deletes already-signed history.

### State-Proof (MPT) Hardening

The MPT state-commitment structure itself is the v4.0.0 design. What is new in v4.1.0 is resilience
around it, added because the rebuilt engine can revisit an ordinal (propose, abandon, retry) against a
shared state store:

- **State-root divergence detection and prevention.** A node that reconstructs state differing from the
  signed snapshot is detected rather than silently continuing on a forked state.
- **Savepoint and full resync.** A round's state mutations can be rolled back cleanly if the round is
  abandoned, and a node can rebuild its state in one shot to a known-good root.

### Consensus Plane vs Data Plane Separation

A significant share of MainNet instability was operational rather than protocol-level: state transfer
(large snapshot streams) was competing with consensus for the same resources. v4.1.0 treats consensus
as votes over small hashes and state transfer as a separate, bounded data plane, with snapshot egress
throttling and connection limits so that catching up a lagging peer does not starve the consensus loop.

### Delegated Rewards Follow the Committee

Delegated reward distribution follows the frozen round-start signing committee directly, independent
of the finalized proof subset. A short, bounded signature grace window keeps late-but-honest signers
represented in the artifact and participation evidence, while validator reward share reflects
actual participation rather than which node happened to sign first.

## Deploy Model: Coordinated Cold Restart (mandatory)

**This release deploys via a full, all-or-nothing coordinated cold restart. There are no rolling
upgrades on any environment.** The v4.1.0 release reports a version hash and folds the consensus
configuration, including the consensus schema version, into a deterministic config hash. The version
hash is checked at joining; the config hash is checked at joining when both peers provide it and on
every consensus round. A mixed-version cluster therefore partitions. The advertised jar hash is
metadata and is not compared during joining, so artifact identity must also be verified operationally.

Restart is from a recent agreed **checkpoint snapshot, never a genesis replay.** Already-signed history
is preserved, and the new jar must re-derive it byte-for-byte, which is what the ordinal gates below
guarantee.

Deploy sequence (full detail in [`v4-launch-runbook.md`](v4-launch-runbook.md)):

1. Quiesce the network and hard-kill the JVMs on every peer (no overlap).
2. Confirm the launch jar is staged everywhere and the gate-ordinal checklist has been baked into the
   jar-packaged config before assembly.
3. Bring up source / priority peers first; confirm each reaches `Ready`.
4. Bring up the remaining peers (matching version and config hashes admit them).
5. Only then re-enable auto-restart monitoring.

### Pre-deploy prerequisites (Release Policy)

- **Snapshot streaming must support sub-trie roots before ordinal `5880000`.** The service
  independently re-derives the signed state proof and must use the same proof shape when the gate
  activates.
- **The six feature flags do not activate at restart.** They activate together when the signed Global
  Snapshot ordinal reaches `5880000`, expected approximately 2026-08-04. Currency L1 and ML0 nodes
  must be upgraded before that boundary for fee-transaction security.
- **Breaking-change commit.** The breaking change is carried by the v4.1.0 integration (#1523,
  `feat: integrate v4.1.0 consensus and MPT line ...`). Confirm it is the discoverable conventional-commit
  record for this release; consider a `BREAKING CHANGE:` footer for explicitness.

## What This Means for Node Operators

The move to a bounded quorum-bearing core with pacemaker-driven view changes raises the importance of
node availability, and rewards it. A healthy, responsive node participates on a level playing field.
A node that drops out during its turn is routed around: the network does not wedge waiting for it, but
it also does not participate (or earn) while it is behind. There is no slashing. Availability is now
the primary determinant of consensus participation.

Because the deploy is a coordinated cold restart gated on a config hash, **every node must run the same
jar and the same per-environment config.** Running a stale jar or an edited consensus config will not
"mostly work"; the node will be refused at the handshake.

## Bug Fixes and Stability

The bulk of this release is stabilization. Grouped by theme:

- **Determinism.** Consensus-critical state (committee, leader, penalties, quality history) is now
  derived from signed chain evidence rather than any local, per-node sidecar, eliminating the
  cold-start and mid-round divergence that produced most observed forks.
- **Recovery.** Fixed circular recovery deadlocks (recovering nodes selecting other recovering nodes as
  sources), tip-chasing during catch-up, and unsafe backward rollbacks.
- **Liveness under degradation.** Leader rotation excludes recently non-participating and
  self-reported-degraded peers; a stalled committee has certified paths to advance the view and, on
  Testnet, to reduce its quorum denominator rather than wedge.
- **Resource pressure.** Snapshot-egress throttling, connection caps, and rate-limit tuning stop state
  transfer from starving consensus.
- **State proofs.** MPT state-root divergence is detected and prevented; savepoint/resync makes
  round abandonment and catch-up safe against the shared state store.
- **Rewards.** Delegated reward share follows the frozen Core + Tier-1 committee, not the proof subset;
  the grace window preserves late signatures and withdrawals expiring together no longer drop rewards.

### IntegrationNet deploy consideration: quorum-shrink is disabled

On IntegrationNet, `core-committee-size` is 9 (a 6-of-9 supermajority core) and
`quorum-shrink-activation-views` is 0, meaning the quorum-shrink liveness rung is **disabled**. On
Testnet the rung is enabled (`10`) and acts as an escape hatch: if enough core peers go silent that the
normal quorum cannot be met, the denominator is deterministically reduced rather than letting the
committee wedge. With it disabled on IntegrationNet, a loss of 4 or more of the 9 core peers can wedge
consensus with no automatic recovery, which is the exact degradation class this release targets.

Because `quorum-shrink-activation-views` is folded into the deterministic config hash, this must be
decided **before the IntegrationNet jar is assembled**. Recommendation: enable it on IntegrationNet for
this promotion (mirroring Testnet) unless there is a specific reason to hold it at 0.
