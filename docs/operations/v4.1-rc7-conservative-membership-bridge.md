# v4.1 rc.7 conservative Global L0 membership bridge

This bridge is built directly on `v4.1.0-rc.6`. Its first objective is to stop the
health-derived membership ratchet that repeatedly reduced IntegrationNet to a terminally small
committee. It deliberately prefers a visible halt requiring operator recovery over silently
deleting signing leases until the network can no longer recover.

It cannot make an arbitrary `SessionStarted` peer join, merge isolated rollback sessions, repair a
failed download, or repair an already impossible frozen committee. It does let a fully downloaded
GL0 probation peer remain probeable in `Observing` until a certificate clears its gate and normal
initialization can finish. Operations must still start from a demonstrably viable anchor.

## Protocol contract

Global L0 creates no new automatic signing-lease removal debt from transient health evidence:

- a Facility with a mismatching facilitator hash is excluded from that Facility set, but does not
  persist a membership removal or penalty;
- proactive Tier-1 and generic B1 eviction votes are not emitted;
- inbound eviction votes are ignored, certificates are not assembled or attached, and a proposal
  carrying a non-empty eviction-certificate list is rejected;
- a certified view change or timeout may advance the view, but GL0 restores the active facilitator
  list from the frozen round-start committee and preserves frozen Core. The next leader is selected
  from frozen Core, falling back to the frozen round-start committee only if Core is empty. Neither
  membership nor leadership uses node-local withdrawal observations: a locally withdrawn, silent,
  or dead Core peer may consume a view, but honest nodes still enter that view with the same roster
  and leader;
- GL0 MajoritySignature declarations hash that same frozen round-start committee. The mutable active
  set cannot leak local withdrawal timing into `facilitatorsHash`.

The bridge neutralizes an rc.6 anchor's one-round `removedFacilitators` TCA carryover. It deliberately
does not erase longer-lived `removalPenalties`, `penaltyUntil`, or `readmissionCountdown`: those
existing debts still filter the first derived committee and age out through deterministic
maintenance/readmission. Explicit signed withdrawal and administrative eligibility rules such as
seedlist, collateral, and configured facilitator selection remain separate authorities.

Currency L0 explicitly retains rc.6 automatic-removal behavior. The layer choice is represented by
one static, non-serialized `HealthDerivedMembershipPolicy`; it has no codec, hash, configuration, or
wire representation. Currency consensus behavior is unchanged; the shared HTTP server/client also
exposes the new authenticated chain-tip-only operational route.

### Deliberately retained rc.6 behavior

`RetainSigningLeases` freezes neither health classification nor the initial leader-eligibility
filter. Existing deterministic tier transitions may demote Core to Tier-1 without deleting the
signing/reward seat, and the initial leader pool may narrow to the configured minimum (currently
two). That preserves the intended Core-as-healthy-subset model but leaves the known
leader-pool-of-two stall class possible. Raising the leader-pool fallback threshold is deferred to a
separate reviewed change; monitor Core identity, leader-pool size, and repeated leaders explicitly.

Explicit withdrawal mutates the in-round active set from locally observed declarations, so it is
not a safe input to deterministic next-view leader selection. A dead or withdrawn Core slot can
therefore add a timeout/view-change cycle. Rendezvous selection visits the frozen pool
deterministically; this churn is self-healing only while enough live Core peers remain to certify the
next view. Canonical current-round withdrawal exclusion requires certified, proposal-carried
evidence and belongs to the v35-or-later design rather than this schema-neutral bridge.

Quorum-denominator shrink is also separate from membership mutation. IntegrationNet must retain
`quorum-shrink-activation-views = 0` for this bridge. A nonzero value can lower VCC, TC, and finality
denominators without deleting a seat and invalidates this soak's safety assumptions. Testnet's value
has historically differed, so testnet is not a substitute for an IntegrationNet-config soak.

The complete residual contraction inventory is therefore: carried penalty/probation debt;
seedlist/collateral/configured facilitator selection; carried Witness classification; explicit
withdrawal; Core/leader quality classification; and explicit rollback/download outcome replacement.
None may be confused with the automatic removal paths disabled by this bridge.

### Bootstrap production pacing

The bridge restores the existing GL0 EventTrigger guard's intended distinction between solo and
multi-node production. Previously GL0 passed `lastOutcome.facilitators.size` to that guard. That is
a membership count, not a participation count: after rc.6 retained silent Tier-1 seats, one actual
signer plus one silent seat looked like a multi-node round and transaction events could start a new
round every five-second cooldown.

GL0 now counts unique proof signers from the last artifact that are also members of the carried
facilitator set. EventTrigger requires at least the existing `bootstrapCompleteProofsThreshold`,
with an absolute minimum of two participants. IntegrationNet's unchanged threshold is three, so
zero, one, or two actual participants are TimeTrigger-paced and three or more retain event-driven
behavior. Events still enter the mempool and gossip, and IntegrationNet's existing 43-second
TimeTrigger continues to advance the chain. A two-validator deployment that follows the existing
operator guidance and configures its threshold to two retains two-node EventTrigger behavior. The
intersection also prevents historical checkpoint proofs outside a synthetic recovery committee
from bypassing the guard.

This proof count is node-local pacing evidence only. It does not enter proposal validation,
membership derivation, snapshot bytes, state proofs, or any deterministic decision. Currency L0 is
unchanged.

This reuses the already-loaded numeric threshold but applies it to local proof participation; normal
bootstrap classification continues to use canonical committee size. It does not add or change a
config value. Any future operator change to this threshold affects both bootstrap classification and
GL0 EventTrigger pacing. Do not set
`bootstrapCompleteProofsThreshold = 1` as a substitute. Such a deployment change alters the deterministic
config hash and, with this bridge's exact next-seat headroom invariant, post-bootstrap singleton
admission would require two existing signers and could never grow `1 -> 2`. Also, during normal GL0
consensus `recentProofSizes` records canonical frozen committee size, not locally observed artifact
proof count. A completed committee of at least three therefore exits bootstrap even if nodes retain
different valid proof subsets. The rolling bootstrap/finality exemption and the rollback
first-round maximum-delay escape remain unchanged and require separate design review.

The bootstrap liveness exemption itself is still needed. A genesis or rollback producer may have to
advance the chain before downloading validators can complete their observe phase. DAG rollback
therefore waits for a feasible Ready quorum, but after at most two TimeTrigger intervals it permits
the recovery producer to start. The current rollback committee preserves every signer from a
non-empty checkpoint proof set and falls back to self only for a proofless checkpoint. A historical
unconditional self-only rollback was reverted after it caused widespread solo production, so this
bridge does not restore it.

Do not condition consensus or finality on locally observed Ready/cluster size. Those views differ
between honest nodes. The new check is safe precisely because it controls only local EventTrigger
pacing; it does not decide who may sign or which snapshot is valid.

## Admission contract

Every post-bootstrap admission lane uses the same local finality-headroom invariant:

```text
Before voting to add A seats: observed current-committee parent signers >= Q(N + A)
```

`N` is the frozen Core + Tier-1 committee and `A` is the largest admission batch a proposal may
carry. IntegrationNet currently has `A=1`. Local proof subsets decide only whether this node emits a
vote. They never enter proposal validation or deterministic state; the existing quorum-certified
`AdmissionCertificate` remains the membership authority.

Open Ready-at-tip admission retains its five-round cadence. Probation recovery remains off cadence,
but no longer bypasses headroom. Global L0 probes one deterministic target in each lane
independently. The probation target is probed at most once per local one-second maximum-poll interval;
it requires the existing configured observation streak (compiled default: two) of fresh responses that exactly name the parent
ordinal and hash, resets on an attempted failure, and never walks to a second probation target.
Throttled ticks preserve history but cannot emit a vote. The open target remains one-shot per monitor
attempt, Ready-only, and reuses authenticated snapshot metadata. It is probed even when a cached gossip
tip looks sufficiently recent. The voter waits for that target's authenticated Facility bound to the same
current round before spending its one-shot probe, so a slightly delayed Facility can still be observed
later in the cadence round. The target becomes vote-eligible only when the subsequent fresh response
exactly names the parent ordinal and hash. A stale/conflicting/failed probe invalidates any cached entry and
causes abstention; a missing or mismatched Facility does the same. This closes the case where a Ready
follower one round behind was seated and then remained permanently late. The
probation lane reuses the existing IHave `ChainTip` type/source through a chain-tip-only
authenticated endpoint and may inspect `Observing`, `WaitingForReady`, or `Ready`: this is necessary
because a carried probation peer is deliberately prevented from reaching Ready until its
certificate clears. The two lane probes and vote budgets are independent: an unavailable probation target cannot
consume or suppress the fixed open target. Proposal construction still applies the existing shared
certificate cap, so independently formed certificates cannot add more than the configured batch.
Currency keeps its legacy cached-mesh evidence and has no direct probe.

The parent Proposal's open nominee is selected by deterministic rendezvous rank. Parent entropy changes
the ranking from round to round, so recovery from a three-member committee is not pinned to a global
"fourth PeerId." Selection is not random per node, however, and rendezvous provides no cooldown: the
same eligible peer can win consecutive parents. The exact-tip/Facility gate makes repeated selection of
an unaligned peer an abstention rather than a bad seat. It does not evict a peer after that peer has been
certified and seated; post-admission replacement is separate follow-on work.

On GL0, probation presence opens the pre-proposal grace before the first admission vote exists. Its
bounded duration is the existing 1.5-second open grace plus `(required fresh observations + 1) ×
max(probe interval, probe timeout)`; with the compiled default of two observations this is 4.5
seconds. The extra interval is assembly/gossip slack, while retaining the base grace prevents state
creation and monitor scheduling from consuming the probe window. A formed certificate closes the grace immediately, and
an unavailable target cannot delay a round beyond that bound. Currency retains its rc.6 grace
calculation.

The GL0 advancer deliberately does not consume node-local proof/headroom evidence. Consequently,
probation also incurs this bounded grace when the local vote-emission gate is closed. For example,
`N=3, S=2` waits up to 4.5 seconds per round while probation remains, but still cannot add the
fourth seat until `S=3`; the delay ends when a certificate forms or the carried debt clears.

## Compatibility and rollout boundary

This bridge adds no consensus message, proposal field, codec, snapshot/state-proof field, hash
construction, deterministic configuration value, consensus config version, or activation ordinal.
It reuses `SnapshotMetadata`, `ChainTip`, `AdmissionVote`, and `AdmissionCertificate`. The new
authenticated chain-tip-only P2P route is operational transport over the existing `ChainTip` JSON
codec; it is not signed consensus state and requires no metagraph coordination.

It is nevertheless not mixed-version safe: rc.6 may emit/apply eviction certificates and shrink on a
timeout certificate, while rc.7 rejects and preserves those paths. Deploy one identical assembly in
a coordinated full-cluster cold restart.

Keep the release-version and deterministic-config fingerprints distinct:

- `versionHash` is the hard join fence. It hashes the embedded `BuildInfo.version` unless
  `CL_VERSION_HASH` supplies an opaque literal override. The official IntegrationNet workflow must
  tag and build this commit as `v4.1.0-rc.7`; an rc.6 peer then fails the two-way join handshake.
  `RegistrationRequest.jar` is separate metadata and is not compared.
- `deterministicConfigHash` fingerprints the consensus configuration and must remain byte-identical
  fleet-wide. In the current rc.6/rc.7 wiring it is carried on Facilities for mismatch diagnostics,
  but it is not a substitute for the release-version join fence: shared startup leaves the optional
  registration value unset, and a Facility mismatch is logged rather than rejected.

The version check happens when a peer joins; it does not expel a process that was already connected.
Stop the entire fleet before starting any rc.7 process, use one official tagged artifact, and leave
`CL_VERSION_HASH` unset. Verify commit SHA, assembly SHA-256, `/node/info` reports
`4.1.0-rc.7`, every `/registration/request` exposes the same effective version hash and that it
differs from rc.6, and deterministic config hash, seedlist, anchor, activation settings, and
effective `quorum-shrink-activation-views = 0` agree on every eligible Global L0 node. No rc.6 node
may remain running or rejoin as a facilitator. Metagraphs do not need an upgrade for this bridge.

## Availability SLO

For IntegrationNet:

```text
N = frozen Core + Tier-1 committee size
Q(N) = ceil(2N/3)
S = valid observed signers from that committee
finality margin = S - Q(N)
```

- `S >= Q(N)`: finality is feasible.
- `S = Q(N)`: the round has no remaining signer-failure margin.
- `S < Q(N)`: rc.7 intentionally halts instead of deleting seats. Restore retained members or run
  an operator-authorized cold restart from a viable anchor.

Outside bootstrap, Tier-1 remains in the finality denominator. Core controls leadership and liveness
machinery, but silent Tier-1 seats consume finality margin. This bridge does not change that pre-v35
architecture; it prevents the attempted repair from ratcheting membership downward.

Two observed signers are not enough information. Record both `N` and `S`:

| State | Result |
| --- | --- |
| `N=2, S=2` | Finalizes at `Q(2)=2`; may admit one Ready peer because `Q(3)=2`. |
| `N=3, S=2` | Finalizes at `Q(3)=2`, but cannot admit into `N=4` because `Q(4)=3`; pinned until the third member signs or operators reseed. |
| `N>=4, S=2` | Cannot finalize; rc.7 cannot recover this state in place. |

The open probe supplies fresh evidence only for an already-`Ready` candidate. The probation probe
can unblock a peer intentionally held in pre-Ready recovery after it has downloaded the exact
parent, but it cannot itself join clusters, complete a download, or promote an arbitrary
`SessionStarted` peer. Therefore `N=2, S=2` can grow only after at least one candidate independently
reaches `Observing`/`WaitingForReady` in the carried-probation lane or `Ready` in the open lane.
With fewer than three proof signers from the current committee under IntegrationNet's existing
threshold, GL0 is additionally TimeTrigger-paced. This slows one- and two-signer recovery producers
without changing their finality or admission authority.

## Anchor preflight

Never choose an anchor by recency alone. Record and verify:

- snapshot ordinal, hash, parent hash, bytes, and unique proof signer IDs `P`;
- `Q(|P|)` and which members of `P` can actually participate;
- operational sidecar hashes/content on every rollback source (mismatch is a stop condition);
- carried penalties, probation, recent signers, tiers, and controller evidence;
- MPT checkpoint consistency and snapshot-streaming fork-row alignment.

Before deploy, run the actual state-creator filters over the anchor and record the derived first-round
facilitator, Core, Tier-1, Witness, and leader-pool identities. This calculation must include
seedlist/collateral/configured selection, active `removalPenalties`, active `penaltyUntil`,
`readmissionCountdown`, carried tiers, and explicit withdrawals. Stop unless the derived signing set
has an operational quorum in one cluster/session and the leader pool is viable. Also stop if the
rc.6 last-resort `allEligible` fallback would have to bypass probation; that fallback can seat peers
whose local initialization gate correctly prevents them from facilitating.

The anchor is viable only when quorum members of the derived first-round signing set can become
consensus-active in the same cluster/session. Running processes or independent HTTP `Ready`
responses do not establish this. Two isolated `run-rollback` sessions do not form a two-peer quorum.
For normal post-bootstrap recovery, use `N>=2, S>=2`: a singleton can produce, but the exact headroom
gate cannot grow `1 -> 2` when `Q(2)=2`. A singleton is a temporary producer only unless the signed
anchor is genuinely still in bootstrap or a separately reviewed, explicitly authorized recovery
seed procedure changes the starting committee.

Disable automatic restart/rollback loops before recovery. Repeated restarts mint sessions, interrupt
downloads, and can keep the non-signing population permanently outside `Ready`.

## Soak procedure

Before restart, archive active and rotated logs, pause transaction load, and record `N`, `S`,
`Q(N)`, margin, exact committee/Core/Tier-1 IDs, node-state counts, rewards, anchor data, sidecar
hashes, and jar/config hashes.

At startup verify:

1. Every node agrees on ordinal/hash, committee identity, rewards, and finality requirement.
2. Tier-1 audits report `disabled_by_membership_policy`; generic eviction emission, ECS assembly,
   proposal ECS, accepted ECS, and new health-removal penalties remain zero.
3. A timeout view advance logs `toSize == frozen round-start N`, no certified shrink, and
   `disabled_by_policy`; Core identity remains unchanged. `fromSize < toSize` is expected when the
   certified view change restores a peer removed only by a node-local withdrawal observation.
4. Any `ecs_disabled_by_membership_policy` proposal rejection means an old or divergent peer is
   present. Abort rather than continuing a partial rollout.
5. Sample node state directly. `SessionStarted`/download counts must decrease without restart churn;
   do not infer readiness only from the load balancer or gossip cache.
6. A carried probation peer may remain stably `Observing` while
   `dag_consensus_init_download_probation_deferred_total` increases. It must answer the exact-parent
   chain-tip probe, receive a certificate, and then complete initialization; it must not bounce
   through `WaitingForDownload` or consume recovery-attempt counters for probation alone.

For each growth step, confirm an open candidate is genuinely `Ready`, returns the exact parent from
the fresh direct metadata probe, and emits a Facility bound to the Core voter's current round (or a
probation target is in an allowed pre-Ready recovery state). Headroom must be non-negative, the
configured fresh probation-observation streak (when applicable) must occur, and at most the
configured batch may be applied. Open admission requires the
Core voter pool. Probation preserves the existing wider recovery witness pool and requires the same
Core-sized count of unique eligible/historical witness signatures; every witness independently
passes the local headroom gate. After `2 -> 3`, the third peer must actually sign before expecting
`3 -> 4`. Join peers in controlled cohorts and keep snapshot-serving throttles enabled.

Soak quietly first, then add controlled transaction load. Track committee/Core/Tier-1 size, proofs,
`Q(N)`, margin, admissions, suppression counters, view changes, round duration, soft resets,
cross-node artifact/state/reward hashes, and node-state distribution.

Abort on `S < Q(N)`, cross-node disagreement, any applied ECS or TC membership shrink, automatic
health-derived contraction, an old build participating, repeated fresh-ready observations without an
admission certificate, ineffective restart cycles, no new `ROUND_STARTED`, or SIGKILL shutdowns.

## Relationship to v35

The bridge is schema-neutral and ships before v35. Port it as a distinct commit onto develop, then
rebase v35 on it. `RetainSigningLeases` must remain active before and after v35 activation; merge
resolution must not re-enable Facility removal, ECS, or TC shrink. Dormant v35 behavior must be
byte-identical to this bridge before an activation is scheduled.

This is a semantic port, not an automatic conflict choice. The current v35 branch overlaps the
bridge at the state creator, advancer, event loop, rumor handler, and state transitions. Its rebase
must preserve all of the following rc.7 invariants on GL0 at both dormant and active keys:

- forked Facility declarations do not create removal debt;
- proactive eviction voting, inbound eviction-vote acceptance, ECS assembly, proposal validation,
  and ECS application remain disabled by `RetainSigningLeases`;
- carried rc.6 `removedFacilitators` do not feed the next state-creator TCA filter;
- timeout certificates never shrink GL0 membership, and next-view leadership uses frozen Core with
  the frozen round-start committee as the Core-empty fallback;
- open and probation admissions share the exact next-seat headroom invariant and proposal cap, while
  retaining their separate cadence and probe rules; open nominees additionally require exact direct
  parent metadata plus a current-round Facility before local vote emission; and
- GL0 EventTrigger pacing uses actual carried-committee proof participation rather than committee
  membership size.

The v35 branch's certified N+1 membership rule is structurally compatible with this bridge, but its
current automatic eviction policy is not: certification changes when an eviction takes effect, not
whether rc.7 permits health-derived eviction. Re-enabling removal after v35 activation requires the
separate symmetric policy review described below.

v35 still requires community announcement and an activation ordinal. Re-enabling automatic removal
after v35 must be a separate, symmetric, independently reviewed policy—not an incidental merge.
